# PRD Quality Review — LanguageLab

## Overall verdict
This is a disciplined, decision-dense PRD. The thesis is clear: Anki is the only store, and LanguageLab speeds up deck-building and adds a pronunciation loop. The Glossary is precise, failure semantics are explicit, and non-goals are honest. Downstream architecture and UX can build on it with little re-interpretation. The risk is in done-ness. The §9 release gate, which SM-1 says "Validates all FRs", leaves out 11 FRs and almost all NFRs. The core value, draft quality, has no acceptance bar. Whether Reference audio is required at Save is unclear. The deck hierarchy also lets Pronounce Cards leak into ordinary Anki study, which contradicts the Glossary. All of these can be fixed in place. None needs a rethink.

## Decision-readiness — strong
The PRD states decisions as decisions and names what each one gives up. Examples: "Saves are last-write-wins. Detecting conflicts … is not required" (FR-23), "There is no archive, trash or undo" (FR-25), "Anki's exact daily limits, sibling behavior and native ordering are not reproduced" (FR-30), and "Exercises cannot be disabled per Item" (§4.6). The scoring/rating split is stated three times consistently (§1, FR-34, SM-C2), so nobody can misread it. The Open Questions in §10 are genuinely open. The PRD has no `[NOTE FOR PM]` callouts. That is acceptable here because the user has confirmed every assumption, but see the one tension below.

### Findings
- **[medium]** Recording length is deferred as "non-blocking" but shapes the UX (§10 OQ1, FR-31). Azure scripted assessment has per-request duration limits, so a long Sentence Item may fail Assessment. Whether the UI auto-stops recording changes the FR-31 interaction and the UJ-3 flow, so it is not only an architecture detail. *Fix:* Add a consequence to FR-31, for example "Recording stops automatically at the Azure per-request limit; the user sees the limit before recording," or mark OQ1 as blocking for UX.

## Substance over theater — strong
There is one persona, and it drives real decisions: Russian as the translation language, iPhone/iPad/desktop, and the trust JTBD behind NFR-1/NFR-3. The NFRs are product-specific rather than boilerplate. NFR-7 lists exactly which content never reaches logs, and NFR-5 and NFR-6 name concrete network boundaries. The Vision (§1) could not be dropped into another language-learning PRD unchanged, because it names Anki-as-store, four Exercises and the rating rule. No innovation section was padded in. No findings.

## Strategic coherence — adequate
The thesis is stated and the features follow from it. Capture → Draft → Item → four Cards → Sync is a single arc. The MVP is clearly a problem-solving MVP, and the C1–C2 deferral in §7.2 is reasoned ("Deferred until the B2→C1 and A1 milestones show what is needed"). SM-C1 and SM-C2 are real counter-metrics paired with the metrics they balance. The weakness is that the thesis's central promise, speed, is never measured.

### Findings
- **[medium]** The speed thesis has no metric or bound (§1 "makes the slow parts … fast", §2.1 "in under a minute"). No SM, NFR or acceptance criterion carries "under a minute" or any latency for generation, TTS preview or Assessment. SM-2 measures where Items are created, not whether creation became fast. *Fix:* Add an NFR or SM, for example "Capture-to-saved-Item typically under 60 s; Draft generation p50 under N s; Assessment result under N s after recording stops."
- **[low]** SM-3 has no threshold (§8, "don't fall far behind the Study Cards"). An informal review is fine for a personal tool, but "far behind" cannot be judged even informally. *Fix:* Name a rough bound, such as Pronounce due count within ~2× of Study due count over a month, or tag it like SM-2.

## Done-ness clarity — adequate
Most FRs have crisp, testable consequences. FR-16, FR-28, FR-34 and FR-35 are model examples. The §5.2 failure table is something story writers can use directly. The problems are a release gate that does not match its own claim, and a handful of FRs whose central outcome is untestable or ambiguous.

### Findings
- **[high]** The §9 release gate does not cover what SM-1 claims (§8 SM-1 "Validates all FRs"; §9). No acceptance criterion traces to FR-3, FR-4, FR-5, FR-7 (migration), FR-10, FR-11, FR-17 (model fallback), FR-18, FR-24 (regenerate with Preview), FR-26 or FR-30 (queue contents, ordering, empty state). Of the NFRs, only NFR-1 is gated. NFR-5 and NFR-6 (localhost binding, no browser-side credentials) and NFR-7 (content-free logs) are security commitments with no gate. FR-2's "not reachable from the LAN" consequence is also missing from AC2. *Fix:* Add criteria for the missing FRs and NFR-5/6/7, or change SM-1 to name the FRs it validates and state that the rest are verified at story level.
- **[high]** Draft quality, the core value, has no acceptance bar (FR-14, FR-15, AC9). The only gated property is schema validity. The phrases "contextually relevant primary Russian meaning", "short list of alternatives when useful" and "concise" (§4.4) cannot be verified. The addendum says models "should be evaluated with representative English/French/Russian fixtures" (§A2), but nothing makes that a requirement. *Fix:* Add an FR or AC requiring a fixture set (for example, N English and N French Targets with context) and an accept rate judged by the user, or explicitly declare quality judged by use and outside the gate.
- **[high]** It is unclear whether Reference audio is required to save an Item (FR-20, FR-28, FR-31; addendum §A3). FR-20 says "Approved Reference audio is written", which implies it might be absent. The §4.6 table and FR-21 call the audio button "optional", but `Audio` is not marked optional in §A3, while every other optional field is. A Pronounce Card without audio breaks FR-31's "play the Reference audio before the first Attempt". New Items also do not say whether a Preview is required or whether the remembered Voice (FR-29) synthesizes audio automatically. *Fix:* Decide and state either "Save requires saved Reference audio" or "Audio is optional; Pronounce Cards without audio show X," and put that rule in FR-20.
- **[medium]** The pronunciation queue's new-card volume is undefined (FR-30). "Anki's exact daily limits … are not reproduced" plus "contains only new and due Pronounce Cards" reads as every new Pronounce Card becoming available immediately, with no cap. After a batch of 40 Items, the session could start with 40 new cards. That shapes SM-3 directly. *Fix:* State the new-card rule, either "no cap in v1 (deliberate)" or "honors the deck's new-cards/day option."
- **[medium]** Editing the Target text leaves dependent data stale (FR-23, FR-24, FR-19). Editing `Target` in LanguageLab or Anki leaves the Reference audio speaking the old text, and Pronunciation Assessment would score against the new text. Nothing defines whether the user is prompted to regenerate audio or whether a duplicate check runs again. *Fix:* Add a consequence to FR-23, for example "Changing Target text flags the audio as stale and offers regeneration; duplicate check runs again."
- **[medium]** It is unclear which fields generation fills and which fields regeneration covers (FR-14, FR-15, FR-24, §11). The Assumptions Index says Sentence generation fills an "optional Hint", but the FR-15 body omits Hint, and FR-14 (Vocabulary) never says whether Hint or Grammar is generated. FR-24 lists "translations, example, note or Reference audio" but not Hint, Grammar or PartOfSpeech. The Pydantic schemas in §A4 cannot be written from this. *Fix:* Add a per-Category field table marking each field as generated, regenerable or user-only.
- **[low]** Some consequences use adjectives where bounds are needed. FR-3 says "The layout is usable at phone, tablet and desktop widths." FR-6 and AC3 say "makes no unintended changes", where "unintended" cannot be verified; it should be "makes no changes when structure is current". FR-36 and AC20 say "graceful shutdown" without defining it (Ctrl-C/SIGINT?). FR-19's normalization covers "case and surrounding punctuation" but not whitespace collapsing, internal apostrophes (`l'eau` vs `l’eau`) or diacritics in French. *Fix:* Replace each with a concrete condition.
- **[low]** FR-10 and FR-31 have no Consequences block. FR-31's recording format and permission-denied behavior, and FR-10's empty state, are left to inference. *Fix:* Add one or two consequences each.

## Scope honesty — adequate
§6 Non-Goals does real work: "No exact reproduction of Anki's native card queue", "No automatic pronunciation rating". §7.2 and the inline "Out of Scope" in FR-1 head off likely silent assumptions. The open-items density (3 OQs and 9 confirmed assumptions) is appropriate for a personal tool. Two implicit assumptions remain unstated, and one of them contradicts the Glossary.

### Findings
- **[high]** Pronounce Cards can leak into ordinary Anki study (§3 "Pronunciation decks … reviewed only in LanguageLab"; addendum §A3 deck hierarchy). `Pronunciation` sits under the same `LanguageLab` root as `Study`. In AnkiMobile or Desktop, studying the root deck (or a filtered deck) pulls in its subdecks, so Pronounce Cards would show up in Anki. Answering them there bypasses Azure feedback and silently changes the schedule. The addendum's claim that a separate branch "keeps them out of ordinary Anki study" holds only if the user never studies the root. Nothing defines how a Pronounce Card renders in Anki either. *Fix:* Pick one: (a) state the constraint "study only `Study::*` decks" as a user rule; (b) give Pronounce Cards an Anki template that says "Review in LanguageLab"; or (c) restructure the decks so Pronunciation is not a descendant of a study-able parent. Then add an AC.
- **[medium]** The "never damaged" JTBD has no safety net for Setup and migration (§2.1 Emotional JTBD, FR-6, FR-7). NFR-1 bounds the blast radius to the Prefix, but a faulty migration or repair can still corrupt every managed note and its review history, which is years of data by the JTBD's framing. The PRD neither requires a backup before applying changes nor states as a non-goal that it relies on Anki's automatic backups. *Fix:* Add an FR-6/FR-7 consequence ("Setup prompts or triggers an Anki backup before applying") or a Non-Goal that names Anki's own backups as the safety net.
- **[low]** NFR-1's precondition is stated as fact, with no defined behavior if it fails (§5.1 NFR-1, "Inside the Prefix there are no pre-existing user notes"). If the configured Prefix collides with an existing user deck, FR-6's behavior is undefined. *Fix:* Add an FR-5/FR-6 consequence: "Setup detects non-managed resources under the Prefix and refuses to apply."

## Downstream usability — adequate
This PRD is chain-top, so this dimension matters. The Glossary is unusually strong: Capture, Draft, Item, Preview, Save, Attempt, Assessment and Rating are each defined once and used consistently with capitals. IDs are contiguous (UJ-1–6, FR-1–36, NFR-1–11, SM-1–3, SM-C1–C2). Each feature section declares which UJs it realizes. Technical decisions are cleanly separated into the addendum and cross-referenced by FR/NFR ID. The gaps below are minor.

### Findings
- **[medium]** "Note" is overloaded, and field names used as domain terms are not in the Glossary (FR-15 "an optional note on applicable grammar or usage" vs "note" as the Anki note everywhere else; §4.6 table "optional hint"; FR-18 "Mnemonic"; FR-11 "Hint or Example"; SM-3 "Study Cards"). The Sentence `Note` field and the Anki note collide in prose, and an extractor will conflate them. Hint, Mnemonic, Grammar and Example are used as product terms, but only the addendum defines them. "Study Cards" is not a Glossary term; the Glossary has "Study decks". *Fix:* Add Glossary entries for Hint, Mnemonic and Usage note (renaming the field in prose) and replace "Study Cards" with "Cards in Study decks".
- **[low]** The UJ traceability is incomplete (§4.6 "Realizes UJ-2, UJ-4"). FR-22–FR-24 are UJ-5's core (search, open, edit, regenerate), but §4.6 does not list UJ-5. *Fix:* Add UJ-5 to §4.6's Realizes line.

## Shape fit — strong
The tool has a single operator, but it is chain-top with real UX across three device classes. Six UJs with a named protagonist (Oleksii), each carrying device and context inline, are load-bearing here, not over-formalized. Grouping capabilities into §4.1–4.9 with globally numbered FRs suits story slicing. Moving stack, config and the Anki schema into a binding addendum (§0) keeps the PRD at capability level without losing decisions. No findings.

## Mechanical notes
- **Assumptions Index roundtrip:** complete. All 9 inline `[ASSUMPTION]` tags (§3 Pronunciation session, FR-7, FR-8, FR-10, FR-13, FR-15, FR-22, FR-30, SM-2) appear in §11, and §11 has no orphan entries. The user has confirmed all of them, so convert the tags to plain statements and either retitle §11 "Confirmed decisions" or remove it. Downstream workflows treat `[ASSUMPTION]` as open.
- **Index vs. body drift:** the §11 entry for FR-15 mentions "optional Hint", but the FR-15 consequence text does not (see the Done-ness finding).
- **ID continuity:** no gaps or duplicates. All AC references in §9 resolve.
- **Self-referential phrasing:** UJ-4 ("the agreed prompt/back/audio rules") and AC15 ("the agreed prompts, backs, hints") point implicitly at the §4.6 table and FR-21. Name them explicitly so the sections extract cleanly.
- **Naming:** Category "Sentence" vs deck "Sentences" (§A3) is fine, but mention it in the Glossary. "Pronunciation decks" (§3) vs "Pronunciation branch" (§A6) are near-synonyms; pick one.
- **Front matter:** `status: draft`. Update it once these findings are resolved.
